# Electron Updater with Cloudflare R2

This app now supports in-app updates for the installed Windows NSIS build.

The recommended hosting setup is:

- Cloudflare R2
- a custom domain such as `https://updates.yourdomain.com/`
- public HTTPS access to the update files

## How update detection works

When the installed Electron app opens:

1. The app reads the installed version from the packaged app.
2. The updater requests `latest.yml` from the configured `baseUrl`.
3. It compares the hosted version in `latest.yml` with the installed version.
4. If the hosted version is newer, the app shows the update modal.
5. If the user clicks `Update`, the app downloads the installer and blockmap from the same hosted location and then hands off to the installer.

Example:

- installed app version: `1.0.0`
- hosted `latest.yml` version: `1.0.1`
- result: the app detects an update and shows the modal

## Recommended file layout in Cloudflare R2

Host these files at the root of your update domain:

- `latest.yml`
- `Social-Case-Report-Manager-Setup-1.0.1.exe`
- `Social-Case-Report-Manager-Setup-1.0.1.exe.blockmap`
- `release-notes.json`

Example URLs:

- `https://updates.yourdomain.com/latest.yml`
- `https://updates.yourdomain.com/Social-Case-Report-Manager-Setup-1.0.1.exe`
- `https://updates.yourdomain.com/Social-Case-Report-Manager-Setup-1.0.1.exe.blockmap`
- `https://updates.yourdomain.com/release-notes.json`

Important:

- do not rename the generated installer
- do not rename the generated blockmap
- do not rename `latest.yml`

The updater expects the hosted filenames to match the names generated by the build.

## Step 1: Create the R2 bucket

In Cloudflare:

1. Open R2.
2. Create a bucket for updates.
3. Choose a name such as `csr-updates`.

## Step 2: Expose the bucket through HTTPS

For production use:

1. Connect the bucket to a custom domain.
2. Use a domain such as `updates.yourdomain.com`.
3. Make sure the files are publicly reachable over HTTPS.

Do not rely on temporary or non-production URLs for your main release channel.

## Step 3: Configure the app

Edit:

- [launcher/updater-config.json](c:/Users/Batosai/Desktop/CSR%20GENERATOR%20original/launcher/updater-config.json)

Set values like this:

```json
{
  "enabled": true,
  "provider": "generic",
  "baseUrl": "https://updates.yourdomain.com/",
  "channel": "latest",
  "notesFile": "release-notes.json"
}
```

Notes:

- `baseUrl` must end with `/`
- `enabled` must be `true` for packaged builds that should check for updates
- `notesFile` is optional in practice, but recommended because the modal uses it for the list of improvements and fixes

## Step 4: Prepare release notes

Use:

- [launcher/release-notes.example.json](c:/Users/Batosai/Desktop/CSR%20GENERATOR%20original/launcher/release-notes.example.json)

as the format reference.

Example:

```json
{
  "releases": {
    "1.0.1": {
      "notes": [
        "Improvements and fixes included in this update.",
        "Refined workflow behavior for the latest release."
      ]
    }
  }
}
```

Upload that file as:

- `release-notes.json`

If notes are missing, the app falls back to a generic improvements-and-fixes message.

## Step 5: Build the old version to test detection

To test the updater properly:

1. Set the app version in `package.json` to an older version such as `1.0.0`.
2. Build the release.
3. Install that older version on the target PC.

This installed older version must already include the updater feature.

## Step 6: Build the newer version

After installing the older version:

1. Change `package.json` to a newer version such as `1.0.1`.
2. Build the release again.

The build output should include:

- the NSIS setup EXE
- `latest.yml`
- the setup EXE blockmap

## Step 7: Upload the new version files to R2

Upload the exact generated files from `dist`:

- `latest.yml`
- `Social-Case-Report-Manager-Setup-1.0.1.exe`
- `Social-Case-Report-Manager-Setup-1.0.1.exe.blockmap`
- `release-notes.json`

Do not rename any of them after build.

## Step 8: What the user should see

When the user opens the installed older app:

- the app checks `latest.yml`
- the app detects the newer version
- the modal appears

The modal shows:

- `Update Available`
- the release notes / improvements and fixes
- `Cancel`
- `Update`

Behavior:

- `Cancel` hides it only for that session
- reopening the app shows it again while the installed version is still old
- `Update` downloads the update and installs it
- after the app is updated and reopened, the modal disappears because versions now match

## Troubleshooting

If the modal does not appear:

1. Check that the installed app is the packaged NSIS build, not dev/browser mode.
2. Check that `enabled` is `true` in `updater-config.json` before building.
3. Check that `baseUrl` points to the correct Cloudflare custom domain.
4. Open `https://updates.yourdomain.com/latest.yml` in a browser and confirm it loads.
5. Confirm the hosted version in `latest.yml` is newer than the installed app version.
6. Confirm the installer filename and blockmap filename exactly match what `latest.yml` references.
7. Confirm the older installed app was built from code that already includes the updater feature.

## Safe recommendation

For your project, the safest release process is:

1. Keep the updater disabled by default in source control.
2. Turn it on only when the real Cloudflare update URL is ready.
3. Build the installed NSIS release from that config.
4. Upload only exact generated files.
5. Test with an older installed version before wider deployment.
